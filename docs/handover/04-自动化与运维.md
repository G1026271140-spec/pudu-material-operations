# 自动化与运维

## 1. 运行副本与任务

以下路径为当前部署拓扑，具体采集结果见 `04-verification/runtime-snapshot.json`。源码目录与正式运行目录不是同一副本。

| 组件/计划任务 | 默认位置 | 处理范围 |
| --- | --- | --- |
| `PUDU Material Web App` | `%USERPROFILE%\PuduMaterialWebRunner\repo` | FastAPI/React、登录、页面/API |
| `PUDU Material Cloudflare Tunnel` | `%USERPROFILE%\PuduMaterialWebRunner` | HTTPS 公网入口到本地 8501 |
| `PUDU Submission Worker` | `%LOCALAPPDATA%\PuduSubmissionWorker\repo` | 飞书后台写入队列、检查点、通知 |
| `PUDU Feishu Card Worker` | 以计划任务实际工作目录为准，当前源代码目录 | 长连接消息、卡片与库存机器人 |
| `PUDU Material Cache Refresh` | `%LOCALAPPDATA%\PuduMaterialCacheRunner\repo` | 每日 10:30 / 16:30 物料/图片缓存、份额核对等 |
| `PUDU Contact Cache Refresh` | 同缓存 Runner | 周一/三/五 11:00 通讯录 |
| `PUDU Runtime Watchdog` | `scripts/run_runtime_watchdog.ps1` | 定时检查并拉起关键 Web/Tunnel/Worker |
| `PUDU Global Journey Material Automation` | `extensions/material-automation` | 附件下载解压、识别图片/视频并回写 |
| `PUDU Global Events English Sync` | 同扩展 | 每日 11:00 / 17:30 英文表同步 |
| `PUDU Streamlit Nightly Wake` | 历史脚本 | 当前已禁用，不应作为新环境必装任务 |

素材整理的说明曾写每 4 小时，但本机配置实际 poll 为 3600 秒，以交接配置/运行值为准。扩展需要 `requests` 和可用 7-Zip；启动器不会自动迁移其去重 state 或安装全部扩展。

本机还存在 `PUDU Lead Intake Worker`：不属于当前正式仓库的已集成模块，最近任务结果非零，不能随主系统默认宣称已接管。其入口和依赖需原负责人另行确认。本包仅保留未集成前端草稿，不包含那个外部服务的完整后端。

计划任务 `Ready` 不代表 Web 已停机（wscript 包装器可结束而子进程仍在）；`Running`/`LastTaskResult=267009` 也不代表业务执行成功。必须看进程、日志、health、队列最终结果和飞书业务读回。

## 2. 日志和故障检查

| 现象 | 首查 |
| --- | --- |
| 本地/公网都打不开 | Web `logs/web.log`、端口 8501、Uvicorn 进程、Windows 登录/电源 |
| 本地正常公网异常 | `logs/tunnel.log`、cloudflared、DNS/Public Hostname、域名和 Token |
| 登录失败或反复授权 | 正式域名 Cookie、回调 URL、应用 tenant/企业信息权限、工作台入口、App Secret 是否变化 |
| 品类/图片未更新 | 当前发布代次、cache Runner 日志/校验、Worker 删除屏蔽日志；不要只刷浏览器 |
| 配货页空或慢 | SQLite 记录、本地后台核对错误、源表 `1254607 Data not ready`；页面列表不应等待整表同步 |
| 显示入队但未完成 | 飞书后台任务队列 + 载荷 + 检查点 + Worker `logs/worker.log`，再查最终业务表/消息 |
| 份额未更新 | 行政源表自动化及运行日志、`/api/corporate-exchange-sync`、权限 overlay、定时核对结果 |
| 管理/HR 未收到告警 | 应用可用范围、通知接收角色、消息 API 错误、failure-notices outbox |

提交 Worker 日志位于 `%LOCALAPPDATA%\PuduSubmissionWorker\logs`；缓存日志位于 `%LOCALAPPDATA%\PuduMaterialCacheRunner\logs`；卡片日志以脚本/实际任务目录为准；扩展 `logs/worker.log` 和 `state` 应一并管理。

## 3. SQLite 与持久化状态（不是“一律删了重建”）

默认共享运行目录 `%LOCALAPPDATA%\PuduMaterialOperations`，同一 Windows 用户下 Web 与 Worker 才能自然访问同一库。不同服务账号必须显式配置为共同可访问且有正确 ACL 的路径。

| 状态 | 处理要求 |
| --- | --- |
| `pending_inventory.sqlite3` | 保存未核实普通申请、明细及 `pending_review_actions` 本地操作日志；已核实/驳回单据删除。已确认无未入队动作后，待核实索引可由源表重建 |
| `catalog-deletions-*.sqlite3` | 删除记录屏蔽/失效日志；迁移时保留或完成新快照与所有消费者一致性验证，避免旧选项复活 |
| `submission_receipts.sqlite3` | 提交回执持久化/去重/待发送，需按切换窗口处理，不可随意重发 |
| `task_failure_notices.sqlite3` | 管理/HR 重试和失败告警 outbox，需保留已发状态及待发送项 |
| `work/live-cache` | 发布代次和指针；转交需完整一致，或在目标生成并校验新代次 |
| `work/corporate_exchange_permission_overlay.json` | 最新份额覆盖；先核对再决定恢复/重建，避免旧缓存放出多领额度 |
| 扩展 `state/processed.json` / `event_translation_sync.json` | 自动化去重状态，缺失可能导致重新下载/上传/写入；不能盲目 `--initialize` 覆盖原状态 |

SQLite 路径覆盖键：`PUDU_PENDING_INVENTORY_DB`、`PUDU_CATALOG_DELETIONS_DB`、`PUDU_SUBMISSION_RECEIPTS_DB`、`PUDU_TASK_FAILURE_NOTICES_DB`。仅挂在某个交互终端的环境变量不会自动传到计划任务，应在实际任务运行环境验证。

备份时应使用 SQLite 在线 backup API 或停机一致性备份。状态和日志可能含员工个人信息、申请内容、消息 ID，按受限业务数据移交，不放 Git。

## 4. 云端工作流

- “未核实库存申请单本机同步”：申请单新增/修改触发 `/api/pending-inventory-sync`。
- “文化周边兑换份额即时同步”：行政**源 Base** 的兑换记录新增/修改触发 `/api/corporate-exchange-sync`，不是只盯主 Base 的同名同步表。
- `scripts/configure_pending_inventory_workflow.py` 和 `scripts/configure_corporate_exchange_workflow.py` 可预览现状；带 `--apply` 才改动。
- 两个接口当前使用 `CORPORATE_EXCHANGE_WEBHOOK_TOKEN`，不能只轮换服务器而遗漏云端流程。
- 工作流在飞书多维表格的“自动化”中，Windows 批量补偿核对在任务计划程序中，两者不是同一套运行日志。

## 5. 扩展迁移提示

复制 `config.toml.example` 并按新机修改 `credentials_file`、素材下载目录及表定位符，复用营销物料管理应用身份。素材扩展可用 `material_automation.py --check` 检查；`--once` 会处理业务、`--initialize` 会建立基线。安装脚本会 initialize，迁移已有去重状态时需先审核这一步。

`event_translation_sync.py` 源/目标 Base 和表 ID 当前为代码常量；公司如更换源表需修改并测试。其安装脚本从 PATH 选 Python，新机须确保选的是装有依赖的运行环境，而不是另一套系统 Python。

## 6. 后续代码发布

在正式 Git master 工作副本进行：版本升级 → 前端构建 → pytest 与缓存/发布一致性验证 → 重建安装器 → 明确选择变更提交推送 → 同步所有运行副本 → 重启受影响组件 → 本地/公网 health → 业务读回和消息验证。不能把源目录更新当作生产已更新。

`scripts/run_release.ps1` 可能执行缓存维护、推送和运行组件重启，交接人员先读脚本/使用 `-PreflightOnly`，不要在接管未完成时直接运行完整发布。`full_feishu_smoke_test.py` 等实表测试脚本也不能未经确认对生产执行。
