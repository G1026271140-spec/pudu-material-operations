# 部署与迁移操作说明

## 1. 先准备账号与独立环境

1. 数字化运营先获得私有仓库权限。当前仓库为 `G1026271140-spec/pudu-material-operations`，正式分支 `master`。受管电脑应能通过已批准的 Git 凭据访问仓库；不要把 PAT 放进 Git URL。
2. 使用固定 Windows 运行账号，确认其登录、网络、磁盘、自动启动和电源策略。现有任务多为该用户登录后运行，不可声称“不登录 Windows 也必然运行”。如改为 Windows 服务/服务器容器，属于后续迁移工程。
3. 当前安装器按需联网安装 Git、Python 3.12、cloudflared 和 Python 包，不是完全离线包。构建前端另需与当前 Vite/TypeScript 兼容的 Node.js/npm；可沿用已打包的 dist。
4. 新节点先用“备用节点”模式。启动器不会自动停止旧节点；未经切换确认，不要在两台电脑同时启用 Worker/缓存写回/定时扩展。

## 2. 用启动器配置

运行 `03-installation/PUDU Material Operations Setup.exe`，由当前部署者确认管理员权限、安装目录、仓库和分支、域名、本地端口、飞书及 Tunnel 配置。第一阶段选备用节点。

本交接安装器从不含业务数据的源码重新构建。它与旧安装器具有相同部署逻辑，**没有自动补齐尚未交接的 Secret、源表权限和运行状态**。其 Git Runner 安装仍需访问私有仓库；不要把“带项目快照”等同于“不需要 GitHub 权限”。

GUI 不一定展示后续业务新增的所有密钥。配置后必须对照 `03-配置与权限交接.md` 补齐 `.streamlit/secrets.toml`，尤其是行政源 Base、同步回调密钥，且所有运行副本一致。重复运行启动器可能重写配置，应先备份并核对高级配置。

## 3. 源码方式准备（在新目录执行）

```powershell
# 当前目录切换到解压后的 01-source，或有访问权限的 Git master 工作副本。
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m pip install -r extensions\material-automation\requirements.txt
Copy-Item -LiteralPath .streamlit\secrets.toml.example -Destination .streamlit\secrets.toml
# 编辑 secrets.toml 和 config/project_config.json；不要直接运行占位配置。
```

需要重建前端时：进入 `request_web/frontend` 执行 `npm ci`、`npm run build`。运行时由 FastAPI 服务 dist，而非 npm dev。

源码 ZIP 不含 `.git`。涉及 `git ls-files`、ff-only 拉取和自动发布的脚本必须在有正确 origin/master 的正式 Git 工作副本执行，不能直接对解压目录运行并期待成功。仓库转交到组织账号时，需同步修改 project_config、启动器默认配置、各 Runner origin 和 CI；只改变网页标题不会迁移仓库。

## 4. 缓存初始化与真实数据边界

本包 `data/` 无真实业务快照。推荐接管时由原维护人安全转交**同一切换时点的、已校验**页面/通讯录/仓位快照，在受限环境放回配置目录及需要的 Runner，或在获授权后重新生成。不同代次快照不能随意混搭。

下列命令是在密钥与表权限正确后执行的初始化示例，并非本次已经在新机执行：

```powershell
.\.venv\Scripts\python.exe scripts\check_feishu_bitable.py
# 下面页面缓存生成器不完全只读：会维护文化周边可申领字段和礼品关联。
# 先经业务负责人确认目标是正确生产/测试 Base，再执行。
.\.venv\Scripts\python.exe scripts\generate_page_data_cache.py
.\.venv\Scripts\python.exe scripts\generate_request_form_cache.py
.\.venv\Scripts\python.exe scripts\generate_contact_departments_cache.py
.\.venv\Scripts\python.exe scripts\validate_page_data_cache.py
.\.venv\Scripts\python.exe scripts\validate_request_form_cache.py
```

首次只想核对配额时运行 `scripts/reconcile_corporate_apparel_quotas.py`，不带 `--apply` 为预览。带 `--apply` 会修改权限份额和新增人员，须业务批准后执行。完整缓存计划任务还包含库存状态维护/份额核对/推送，不可当作无副作用只读命令。

仓位缓存是人工发布范围，不参加日常全部缓存刷新。由业务负责人决定是否安全转交原快照；只有明确需要更新时才执行 `scripts/generate_warehouse_location_cache.py`。

缓存副本齐备后可用本地命令启动技术验证：

```powershell
.\.venv\Scripts\python.exe -m uvicorn request_web.api:api --host 127.0.0.1 --port 8501
```

**注意：启动 FastAPI 也会启动提交回执与待核实同步后台线程。** 即使没有启用提交 Worker，也不是完全隔离的测试环境。要做无生产副作用验证，应使用测试应用/Base/回调密钥及隔离 SQLite 路径，不要把生产通知 outbox 复制到测试机。

## 5. 域名与飞书登录

域名必须属于部署者并接入其 Cloudflare 账号。自动配置模式提供限定到目标账号/Zone 的 Tunnel 与 DNS 编辑权限 Token；运行阶段使用 Named Tunnel 运行 Token，不需保留管理 API Token。

更换域名时同步：Cloudflare DNS 和 ingress → `deployment.custom_domain` → 各 Runner 有效公网 URL → 飞书网页应用主页/移动端主页 → OAuth 回调 `https://新域名/auth/feishu/callback` → 工作台入口 `https://新域名/auth/feishu/workplace-start` → Base 工作流回调地址 → 卡片中的链接。旧域名不要在登录、写入、卡片、回调全部验收前移除。

## 6. 正式切换（需双方约定窗口）

1. 盘点后台队列和本地待发送通知/未入队动作；暂停新业务提交，处理或记录在途任务。
2. 先停止/停用旧机器 Watchdog，再停止对应 Web、Worker、卡片、缓存和扩展任务。只停 Worker 而不处理 Watchdog 可能被自动拉起。
3. 通过受限备份保存本地 SQLite（使用 SQLite backup API 或停机后正确处理 WAL）、权限 overlay、live-cache 当前代次以及扩展 state。不要在线只复制 `.sqlite3` 主文件并忽略 WAL。
4. 将确认需要恢复的状态安全移交新机；检查 Windows 用户路径和配置、Base 相同、运行节点/优先级。待核实记录可以从飞书重建，但未入队动作和通知去重状态需逐条确认，不能直接丢弃。
5. 新机按迁移接管模式安装任务；确认旧 Worker/定时写回已停止。安装 Web/Worker/缓存脚本会注册并启动任务，并可能拉取最新 master，不能在无切换授权时试运行。
6. 手动迁移时安装 `install_local_web_app_task.ps1`、`install_submission_worker_task.ps1`、`install_feishu_card_worker_task.ps1`、`install_local_cache_task.ps1`，参数以各脚本头部为准。缓存安装可用 `-SkipInitialRun`，避免未经确认立即全量修改。启动器未包含的 Watchdog 和扩展任务需另行登记。
7. 更新并验证两个 Base 工作流。配置脚本不带 `--apply` 为预览，带上后会写入并启用流程；先检查同名流程，避免重复。
8. 按验收清单验证真实申请 → 配货/驳回 → 后台最终写入 → 通知 → 份额/库存，最后解除提交冻结。
9. 保留旧节点只读回滚备份，不运行后台写入；新环境稳定后再决定轮换/吊销旧凭据。

回滚时先停新节点相关任务和 Watchdog，核对切换期间已完成的队列/数据再恢复旧节点，绝不能同时启动两边来“碰碰运气”。
