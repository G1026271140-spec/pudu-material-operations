# 物料发货日历

入口：后台编辑 → 配货与发货 → 物料发货日历。
同页可切换“配货工作台”和“物料发货日历”；原配货和日历链接均保持可用，浏览器前进、后退和刷新会保留对应子页面。
路由：`/management/shipping-calendar`。企业内已登录申请人可以只读查看本人的单据；已启用管理员可查看全部并编辑。
非管理员只显示发货日历，不开放配货页签。列表和图片均在服务端验证原申请人 open_id；姓名、提交人和客户端查询参数不能扩大范围。

## 展示口径

数据直接读取虚拟机 PostgreSQL 申请单和申请明细；不用页面业务缓存。
仅展示普通物料申请、库存审查状态为“已核实库存”，并排除撤回、驳回、取消中的单据。
未发货和已发货分两列，以原申请单的“是否发货”复选框区分，不能由有无运单号推断。
日历按北京时间计算“今天”；可切换计划发货日、要求到达开始日。
缺少当前依据日期的申请单保留在未设置日期分组；整月视图同时显示这些单据。
支持全部日期及单号、申请人、物料、物流信息搜索。
卡片同时显示发货日与到达日，详情显示全部申请明细和收件信息。
超过计划发货日但未发货的单据显示提示；已发货单据不显示逾期提示。

## 保存和同步

页面先暂存每张申请单的修改，可继续编辑多张；暂存不会修改正式业务字段或发送通知。
点击“统一提交修改”弹窗显示原文：**发货信息即将同步给申请人，请确定提交**。
取消则保留草稿；确定后整批校验版本，在同一短 SQL 事务中写入所有申请单的发货字段及管理员修改的发货日期、审计、幂等结果、ordinary lane outbox 和申请人通知任务。
任意一张冲突或附件无效则整批回滚，不会部分提交。
事务内没有飞书 HTTP 请求。保存返回后页面立即反映本地结果；worker 异步发布到同一申请单。
上传图片先持久化到共享媒体目录及本地媒体表，再由 outbox worker 上传到飞书。
支持 PNG/JPEG/WebP，单张最多 6 MB、2400 万像素、每单最多 12 张。
新增附件必须归属当前上传人，已有附件只能保留当前申请单关联的附件。
图片上传接口仅管理员可用；已保存图片的读取需验证当前账号是该单申请人或已启用管理员，禁止跨单读取和附件注入。
版本检查防止陈旧窗口覆盖新值，幂等标识防止网络重试产生重复写入。
飞书人工修改冲突沿用 outbox 冲突策略；不能静默覆盖。
管理员修改发货日期时，同一事务更新原申请单、申请明细、下单明细和关联批次的日期；通知等待这些对应 outbox 一起完成。
每天 03:00 Asia/Shanghai 的原核对任务继续以飞书为准回写本地，这三个已注册字段自然纳入。
发货编辑不扣减库存、不改变审批状态或申请数量。
申请人通知使用应用身份，接收人严格取原申请单“申请人”账号，不接受前端指定收件人。
每张实际发生变化的单据创建一条通知，含申请单号、发货状态、日期、物流文字、图片数量和本人申请的前端详情链接；
等待该单相关 outbox 全部 done 才发送。等待飞书期间不消耗消息重试次数或去重窗口。
消息超时重试使用相同 Feishu UUID；源字段冲突时暂不通知；新版批次替代尚未尝试的旧通知。
页面显示待通知、已通知或需核对状态。重复提交和无实际变化的单据不产生重复通知。
暂存内容在同一页面会话的页签、侧边栏切换中保留；刷新、关闭前给出离开提醒。
旧单笔保存接口停用，统一使用确认后的 batch 接口。

## 验证

后端测试：`tests/test_shipping_calendar.py`，在隔离 PostgreSQL 中验证字段原子保存、
权限、版本冲突、重复提交、附件归属、完整明细、网络重试和每日飞书优先核对。
前端逻辑测试：Node 22 `node --experimental-strip-types --test request_web/frontend/tests/shippingCalendar.test.mjs`。
测试不得写真实申请或发送员工消息。生产验收只读检查字段、目录、权限和运行版本。

中台角色与管理员均可查看所有符合条件的发货申请、编辑发货日期及三个发货字段、上传图片并统一确认提交。
配货页签、配货查询及提交接口继续仅允许管理员或有效管理员卡片链接，中台不获得配货权限。
普通申请人仍只能查看自己的发货信息。用户权限管理中的中台选项与飞书用户权限表同一角色字段对应。

发货结果为只读 Card 2.0 通知，按钮进入申请人只读视图。全部业务写入及通知完成后，额外发送启用管理员的任务结果回执。
