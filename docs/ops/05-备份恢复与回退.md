# 备份、恢复与回退

## 备份组成和验真

`pudu-material-backup.timer` 每天北京时间 02:40 执行，正式发布前也会备份。受限目录 `shared/backups` 中同一标签有三件：

- `pudu-<时间>.dump`：PostgreSQL custom dump，包含业务、元数据、审计、jobs / outbox / effects 等操作状态。
- `pudu-<时间>-files.tar.gz`：媒体、外置配置、自动化配置及状态；**包含机密**，不能加入 GitLab 或普通交接 ZIP。
- `pudu-<时间>.json`：采集时间、源码 release、文件 SHA-256 和同一数据库快照的逐表摘要。

`.partial` 不是完成备份，不参与恢复。备份有 manifest 还需核对两个文件实际存在、大小和 SHA-256、`pg_restore --list` 可读。数据库摘要来自导出使用的同一个 repeatable-read 快照；不要用持续变化的生产库与旧快照直接比摘要。

V3.9.5 曾将 `pudu-20261028-140725-826653` 恢复到独立库，核对 23 张业务表和 7,115 行时间点数据、全部操作表摘要、媒体 / 配置 / 扩展状态及序列，验证后清理。报告在 `shared/pg-v395-restore-acceptance.json`。这是历史演练证据，不代表任意将来备份都已验证。

## 独立恢复演练

1. 选择完整三件套，验证文件 hash；限制目录权限，不能把配置解包到公共路径。
2. 在管理员控制下创建**新的隔离验证库**，确认目标名字与 `pudu_materials` 不同；使用兼容数据库角色恢复，不对生产 `--clean`。
3. 用 `pg_restore` 恢复到新库，**不启动任何连接真实飞书的 Worker**；测试必须阻止外部飞书 HTTP 或使用模拟器。
4. 在恢复库只读事务中逐表运行 `material_store.backup.fingerprint`，与 manifest 比较业务表、material_meta 和 material_ops。检查序列 nextval 可大于已有最大值，避免恢复后编号冲突。
5. 将媒体、配置和扩展状态解压到隔离的受限目录；验证归档内路径不会逃逸目标目录，并核对文件摘要 / JSON 可读性。
6. 记录所用备份、源 release、恢复库名、表和行数量、摘要、序列、文件结果、清理结果；演练通过后只删除已确认的隔离库和目录。

实际命令中的数据库名、归档路径和角色必须现场核实。本手册不提供一条覆盖生产数据的“快捷恢复”命令；例行需求无须做生产恢复。

## 真正灾难恢复

先明确事故点和丢失窗口，保护故障现场及尚未同步的本地变更。停止所有可能写业务 / 通知的组件：Web、business、effects、card、bridge、assets、english、三个 outbox；同时阻止 reconcile / contacts timer 在恢复期间运行。Cloudflare 外部入口应显示维护状态，禁止新申请进入旧库。

恢复到新库、新受限文件目录并验证，不原地覆盖。对照备份时点之后的 GitLab release、外部飞书已写数据、队列幂等和消息 ID，制定差异处理后再切换有效 DSN / 文件目录。恢复前后都保留原库和配置副本，先只读验收、再放开业务及 timer。不能简单恢复旧 outbox 后立即跑 Worker，否则可能重复扣库 / 重发卡片。

如果 VM 上所有备份都随磁盘一起丢失，当前同机备份无法救回；异机受控存储或公司备份平台需单独接入并验证。本次交接不将“已有本机备份”描述成已具备异地灾备。

## 应用回退与数据恢复不同

发布入口在切换后的健康检查失败时自动恢复旧应用 release，**不恢复旧数据库、不删除 outbox**。通常功能回退应在最新 GitLab 上 `git revert` 产生新的前向提交，再走 `sudo pudu-release`，保证双管理员代码不被旧版本覆盖。

`sudo pudu-release --deploy <SHA>` 只接受当前 GitLab 发布头且为线上后代的已验证版本，不能用它任意切回旧 SHA。涉及数据库结构的回退须评估向后兼容；不要为回退 UI 执行破坏性反向迁移。
