# 每次对话的持续归档

## 两层档案

**可提交的工程记录**存于 `docs/ops/changes`，每次需求或运维处理追加一份，包含输入、决策、执行、验证和遗留事项。根目录 `AGENTS.md` 要求新运维人员 / 新 Codex 聊天接着使用相同模板和发布入口。

**受限的原对话档案**存于交接包 `03-受限对话归档`，VM 副本位于 `shared/handover-archives`。它包含用户文字、可见处理进展和最终答复，已省略推理、系统指令、工具参数及原始输出，敏感值脱敏。不要将整个原始 `.jsonl` 上传 GitLab，它还包含环境指令、工具载荷等无关和可能敏感内容。

## 每次处理的固定顺序

1. 记录聊天 ID / 轮次 ID（平台能取得时）、北京时间、需求原话或准确摘要；明确后续补充如何修正原要求。
2. 写清现状和目标，引用业务规则；未确认字段 / 权限不凭空猜测，先查注册文件、现有代码和只读数据。
3. 记录采取的步骤、修改的文件 / 字段，区分实现、验证与未完成事项。
4. 记录测试环境、命令与结果；不写密码、令牌、人员导出、原始申请详情或凭据文件内容。
5. 代码和工程记录一同提交，再走统一发布。发布证据引用 `shared/release-audit.jsonl` 的实际记录；本地包 manifest 关联当前 release，不为填最终 SHA 改写已发布文件。
6. 报告结果和限制；新规则更新 `02-固定业务规则.md`，遗留事项标明下一步，不写“全部完成”掩盖未验收。

创建模板：

```bash
cd /srv/pudu-materials-workspaces/"$(id -un)"
/home/gaohongyuan1/pudu-materials-operation/venv/bin/python scripts/new_ops_record.py short-task-name
```

纯问答 / 故障核对也可以写一条记录，不为归档重放业务。如果同一个聊天包含多个需求，可在一条记录中列出并分别验收，或拆成多个记录；原轮次 ID 保留追溯关系。

## 导出可取得的 Codex 本地聊天

在拥有原聊天文件的电脑上运行（标准 Python 即可）：

```text
python scripts/export_conversations.py --session <所选聊天的JSONL路径> --title <聊天标题> --out <新的受限输出目录> --attachment-root <原附件目录>
```

每个输出目录包括 README 索引、按轮次的 Markdown、manifest（来源文件摘要 / 数量 / 时间 / 稳定 ID）和仍可取得的用户截图。输出目录必须是新的，避免覆盖旧档案。

导出只读取显式指定的聊天，不扫描无关聊天、不导出工具参数和内部推理，不复制凭据文件。自动脱敏后仍须检查敏感信息；截图按内部业务资料保管，缺失原图只标记缺失，不生成替代图。部分文件链接来自旧电脑，失效时参照记录中的需求文字，不能当作当前服务器路径。

该导出器**不是常驻监听器**，不会自动获得其他电脑或未来新聊天。后续每次处理都需按工程规则补写记录；需要原始聊天时，在取得该聊天文件后显式导出。这避免承诺无法取得的历史和后台自动归档。

## 给新 Codex / 运维人员的开场指令

> 请先读仓库根目录 AGENTS.md 和 docs/ops/README.md，再核对虚拟机当前 GitLab、release、服务、数据库及队列。需求在个人 VM 工作区修改，使用隔离数据库测试，写 docs/ops/changes，提交后 sudo pudu-release，最后核对公网与业务终态。保持 PG 先写、worker 同步飞书、每天北京时间 03:00 飞书优先核对、既有角色和通知规则。不要恢复旧电脑任务，不覆盖其他人的未提交修改。
