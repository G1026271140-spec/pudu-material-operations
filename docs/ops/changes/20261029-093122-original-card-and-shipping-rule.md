## 用户需求与更正

用户指出飞书卡片“按原申请确认”完成后会生成新卡片，要求原卡片自动更新。处理过程中进一步明确：审批通过就勾选已发货；物流文字或发货图片至少一项才给申请人发通知。最新规则替代上一版将完整明细及物流内容同时作为勾选门槛的规则。

## 调查和修改

只读生产审计发现回调任务有原消息 ID，而后续“申请物料库存确认”任务未保留；历史确认任务生成了两条 send_interactive_message。截图对应申请的库存确认卡片仍有登记 ID。本次不代替用户确认真实申请，也不向员工发测试消息。

- scripts/feishu_card_worker.py：将原 message_id 放入确认草稿；幂等键包含消息，兼容不同管理员在各自卡片点击。
- app.py：确认完成和已确认重试均调用 update_only 模式；按稳定申请 ID 读取最新快照，合并回调原 ID 和已登记卡片。禁止读取失败、缺消息或过期后改成发送新卡片；不因管理员名单新增而另发。已有审批实例后的重复确认保留审批数量。
- material_store/jobs.py、effects.py：原卡片更新等待对应业务 outbox，按同单任务顺序更新，防止旧重试覆盖新卡片。
- material_store/auto_shipping.py：原生审批通过独立驱动已发货标记，物流文字或图片控制通知；验证审批属于本单，保留通知幂等及最后发送检查。历史已通过单据只补状态、不补发旧通知，不改明细数量和库存。
- ShippingCalendarPage.tsx：复选框说明同步最新条件；README、固定规则和日历手册同步。无新业务字段或 SQL 迁移，数据先本地后飞书、每天 03:00 校验不变。
