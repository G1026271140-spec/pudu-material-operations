# 日常运维与故障

## 常驻进程和计划任务

| 服务名（加 `pudu-material-` 前缀） | 责任 |
|---|---|
| `web` | 页面、飞书 OAuth、API |
| `business` | 本地领域任务，普通与文化独立业务通道 |
| `outbox@ordinary` / `@cultural` / `@admin` | PostgreSQL → 飞书对应表的变更 |
| `effects` | 数据同步后发送 / 更新持久化通知 |
| `card` | 飞书卡片交互接入 |
| `bridge` | 迁移后保留的旧自动化衔接 |
| `assets` / `english` | 素材和英文相关现有后台处理 |

实际安装的 unit 和 drop-in 是生效配置。仓库中旧 commissioning unit 仅供历史追溯，不能直接覆盖 `/etc/systemd/system`。

| timer | 北京时间 | 内容 |
|---|---|---|
| `pudu-material-backup.timer` | 02:40 | PostgreSQL + 媒体 + 外置配置 / 自动化状态备份 |
| `pudu-material-reconcile.timer` | 03:00 | 全部来源表，以飞书为准核对 PG |
| `pudu-material-contacts.timer` | 03:10 | 完整刷新通讯录，失败保留原数据 |

备份、日校验和通讯录是 oneshot，执行成功后 inactive/dead 正常；查看 timer、`ExecMainStatus=0` 和真实结果记录，不能把未常驻认定异常。日志可能显示 UTC，要转换北京时间核对。

## 后台任务页面

管理员进入“系统工具 → 后台任务”（`/management/tasks`），默认查看全部进行中的本地业务、飞书同步、卡片通知、校验和导入记录，每 2 秒更新。可按状态 / 日期 / 单号查询历史，打开详情查看错误、结果和关联处理链；页面不写飞书，也不提供重放 / 删除操作。后台服务心跳显示最近活动时间。

业务 jobs 在事务提交前仍是 pending，页面用本地执行标记及 PostgreSQL backend 身份显示真实“正在执行”；正式发布也等待有效执行标记归零。历史错误须核对后处理，不能仅为清空计数重新执行库存或通知。

## 只读检查

```bash
cd /home/gaohongyuan1/pudu-materials-operation/source
venv_python=/home/gaohongyuan1/pudu-materials-operation/venv/bin/python
"$venv_python" scripts/ops_status.py
systemctl list-timers 'pudu-material-*' --no-pager
systemctl show pudu-material-reconcile.service -p ExecMainStatus -p ExecMainStartTimestamp -p ExecMainExitTimestamp
sudo journalctl -u pudu-material-outbox@ordinary.service -n 60 --no-pager
```

巡检脚本显式只读事务，只输出聚合状态、版本、服务与备份元数据，不触发同步、重启或通知。队列中历史 failed 不等于当前故障，要结合创建时间、对象和最近业务；不要为了让数字归零重跑业务。

## 页面少单 / 找不到申请

按顺序核对：

1. 获取单号、申请人 open_id、用途和日期；不要凭模糊记忆认定漏同步。
2. 管理员历史页切换“所有数据”，清空搜索 / 状态 / 日期限制。个人数据只能看本人；HR 的全部范围不含全公司普通物料。
3. 配货工作台只看待核实库存，已核实的单据应转发货日历。日历按计划发货日或要求到达日定位对应月份，检查未设置日期分组。
4. 用飞书应用身份完整分页读取申请单和明细，与 PG 按远端记录 ID、单号、父子关联、业务字段对比。数量相等还要检查 ID 集、软删除、孤立明细和重复单号。
5. 若 source / PG 都存在且字段一致，是显示范围或业务状态问题；不要“补导入”再创建一张。

2026-10-28 的法国医疗新展会例子：`REQ-20261019-002`，14 条明细 / 7 品类 / 400 件，已核实库存、计划 11 月 4 日发货；并未漏同步，管理员个人列表及待核实配货列表看不到，11 月发货日历可见。此例只说明排查口径，不固定未来状态。

## 同步积压 / 失败 / 冲突

- `jobs` 是本地业务任务，`outbox` 是飞书数据发布，`effects` 是消息效果，不能混为一条队列。
- 网络故障可让尚未完成的同一 outbox 按原幂等键重试；先确认是否已在飞书创建 / 更新，禁止重新执行库存或发放 job。
- `conflict` 要比较本地补丁、baseline、飞书当前字段、日校验审计；若飞书已由人工更改，先确定业务目标，不直接将所有 conflict 改 pending。
- 消息超时可能已发送，使用原 effect 身份 / UUID 和远端 message_id 查证，不能另建“补发”造成重复。
- 当前只有 ordinary / cultural / admin 消费服务。`notification` 虽存在于数据库枚举，未启独立服务；恢复纯通知回执的字段写入也应走有消费者的适当通道。
- 失败提醒是需核对卡片；不要为修复异常重新恢复已取消的管理员成功回执。

## 每日 03:00 校验失败

先看 `material_ops.reconcile_runs` 最新状态、阶段和 journal，不仅看 timer 是否触发。字段定义不一致时：

1. 逐表比对飞书 schema、`config/feishu_field_registry.json`、`material_meta` 和投影列，保留稳定 field_id；确定新增、删除或类型变化。
2. 制作最小幂等 SQL 迁移，先在隔离库验证；新增列不重写 `_fields`、baseline、版本和历史记录。
3. 备份生产，以 schema owner 的受控权限应用已审查迁移，提交并正式发布。
4. 仅在数据方向已确认后重新运行 reconcile，并核对全表读取终态、业务字段与冲突；这是写操作，不作为例行只读巡检。

V3.9.5 修复了主来源服饰镜像缺少 4 个展示设置字段的问题，并将运行记录提前到预检前，网络 / schema 失败也会留 `failed` 和阶段。不能跳过 schema 校验来“恢复”任务。

2026-10-30 03:00 的历史失败为 Worker session guard 和 claim / claim_more 的跨连接重复共享锁，与排队中的全量独占锁互等；旧任务在 03:15 被 systemd 超时终止。V4.1.7 已将 guard 传给 claim，避免再申请另一连接上的同一共享锁。当天 09:41–09:42 补跑完成全部 23 张表、0 冲突。不要为解除等待直接终止正在处理的业务事务。

校验运行先注册 `reconcile_runs`，再申请全量独占锁。等待最多 120 秒，超时留下 `failed / waiting_lock / reason=lock_timeout` 及耗时，本次尚未读取和应用飞书数据；恢复原 session lock_timeout，不把连接池后续业务设置成短超时。正常阶段依次为 waiting_lock、metadata、source_fetch（显示已读取 / 总表数）、apply、done。手动 / 每日校验共用该逻辑，凌晨 03:00 与飞书为准的方向不变。不要绕过锁或直接重放库存。

## 库存查询与校正

管理员进入“系统工具 → 虚拟数据库 → 库存查询”，筛选品类、型号 / 尺码、语种、战区，也可按编码查找。选择对应行“修改库存”，输入修改后的实际数量及可选说明。页面保存后读取本地结果，后台任务的“库存查询调整”与关联 outbox 可查看最终飞书同步状态。不能把本地已保存当作已同步。

普通物料 / 文化周边对应主来源库存；文化衫对应行政源表，目标数量转换为“入库/纠正”的差额，不清零历史兑换数量或额度，不改写公式结果。整数可为负数以兼容源表欠库；保存保留原有业务通道锁、行锁、角色复核及幂等，失败整体回滚。不用生产库存做测试。

## 域名 / 飞书网络

先分别测试 DNS、TCP/TLS、应用身份认证、Base 读取，避免用个人 OAuth 替代网络修复。域名变更须同时核对 Cloudflare DNS/Tunnel、`PUDU_PUBLIC_ORIGIN` 和有效配置中的域名、飞书 OAuth 回调 `/auth/feishu/callback`、工作台入口、Webhook、卡片链接 / 二维码，再核对新旧入口；不要只改前端文案。
