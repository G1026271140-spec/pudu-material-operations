# 固定的开发与发布流程

唯一生产发布入口为 `sudo pudu-release`。它在整个集成、测试、构建、GitLab 推送和上线过程中持有 `/run/lock/pudu-material-release.lock`。本页描述现有流程，不另建第二套发布工具。

## 1. 明确需求，建立记录

先读 `AGENTS.md` 和本手册，确认触发场景、角色、字段、预期结果和验收方式。创建记录并填入需求 / 后续纠正：

```bash
cd /srv/pudu-materials-workspaces/"$(id -un)"
/home/gaohongyuan1/pudu-materials-operation/venv/bin/python scripts/new_ops_record.py shipping-date-card
```

每次对话形成一条或多条记录；“继续”继承未完成需求，不另建重复业务操作。以用户后续明确更正为准，不执行归档中早已被替换的旧方案。

## 2. 核对环境，更新个人工作区

```bash
git status --short
git branch --show-current
sudo pudu-release --check
git fetch origin codex/postgres-core
git merge --ff-only origin/codex/postgres-core
```

有未提交改动时先确定归属，不能 reset/clean 覆盖。无法快进时保留个人提交，检查差异；正式发布工具会三方合并，不能强行重置他人工作。`repo` 只供发布集成，`source/releases` 不编辑，GitLab 发布头可能比交接包更新。

## 3. 做最小修改

沿用现有 API → domain → repository → outbox → effects 路径，保留事务、幂等、权限和版本顺序。字段变更须核对稳定 ID，形成可重复执行的迁移，在隔离库验证后备份生产再应用。发布命令**不会自动执行所有 SQL 迁移**，不能误以为发版会替你改数据库结构。

不要把生产凭据拷入个人工作区或交接源码；不要借“测试”运行 `full_feishu_smoke_test.py` 等会写真实飞书的脚本。

## 4. 验证受影响功能

```bash
export PUDU_TEST_DATABASE_DSN='dbname=pudu_materials_test'
/home/gaohongyuan1/pudu-materials-operation/venv/bin/python -m pytest tests/test_shipping_card.py tests/test_shipping_access.py -q
```

上例仅适用于发货卡片 / 只读权限变更，其他修改按代码导航选择测试。库存、额度、删除、权限授予、驳回和消息必须用隔离 / 恢复测试库及模拟飞书，不能扣真实库存或给员工发测试卡片。不要并行运行前端 build 和会读取构建产物的测试。

## 5. 记录和提交

在 `docs/ops/changes/<时间>-<主题>.md` 中写明：需求、更改文件、字段影响、测试结果、实际限制；如有新规则更新本手册。检查差异后只 add 本次文件：

```bash
git diff --check
git diff --stat
git add <本次修改的文件及变更记录>
git commit -m "Describe the behavior change"
sudo pudu-release
```

不要直接运行旧 Windows `run_release.ps1`，不要 force-push，不要手动将 `source` 指向某目录，不要 rsync 整个交接包覆盖线上。

## 6. 发布命令具体会做什么

1. 校验调用账号和个人目录、工作区干净；核对集成仓库无未提交修改，读取 GitLab 最新发布头。
2. 创建私有临时构建仓库，三方合并本次个人提交。后提交的一方赢得重叠文本块，非重叠修改保留；结构冲突停止。
3. 自动递增 `APP_VERSION`，运行全部 `tests`（包含隔离 PG）、前端 Node 测试和 TypeScript/Vite build；检查构建产物。
4. 校验 GitLab 头未变化，将 release 提交推送 `codex/postgres-core`，集成仓库快进。
5. 上线前创建备份；确认队列无 processing，停止当前 10 个长驻服务，再检查在途队列、GitLab 头和 release 祖先关系。
6. 创建不可变 release 并原子切换 `source`，启动同一组服务；检查本地与公网健康内容相等、版本正确、业务写入启用。
7. 切换后健康失败则恢复原 release 并启动服务。成功将前后 SHA、版本、操作者和健康结果写入 `shared/release-audit.jsonl`。

测试失败：没有推送 / 上线，先修复再提交。已推送但部署未完成：检查实际状态，必要时使用 `sudo pudu-release --deploy <SHA>`；该 SHA 必须是**当前 GitLab 发布头**且为线上版本的后代，不能部署历史祖先来覆盖新工作。

## 7. 部署后回读和结束归档

运行 `scripts/ops_status.py`，确认 GitLab SHA 与线上 release 对应、所有服务版本和队列正常。通过受影响业务的只读接口 / 源记录核对真实结果。通知只看实际 effect 及远端消息结果，不将 pending 当 sent；冲突 / 失败保留清楚说明。

将发布回执保存到受限运维证据目录；变更记录通过 commit message 和父提交关联 release，不把“预期 SHA”当成实际发布证据。需补充新的实质信息时追加记录并提交，再沿同一路径发布，不能直接改已发布目录。

仅有页面能打开、进程 active、测试通过、GitLab push 或任务入队，都不足以宣布业务修改完成。
